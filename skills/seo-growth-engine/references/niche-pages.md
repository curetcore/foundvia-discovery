# Distinct audience needs

Create a use-case page only when there is a real customer task and useful audience-specific evidence. A changed profession/city name is not distinctive value. Consider improving one shared page when the workflow and evidence are the same.

Brief: audience → specific task → actual workflow → original example → relevant limitations → natural next action. Use real supported features and customer permission for testimonials. Do not fabricate examples, offices, or local statistics.

If implementing data-driven routes, validate records, handle missing slugs with notFound, and build metadata/canonical from the actual record. Render schema safely and only when it describes the page. Avoid a quota of niche pages or mandatory FAQ counts.

Acceptance: an intended customer can complete the described task; each indexable route has a reason to exist beyond replacing a keyword. Revisit overlap and usefulness before scaling.

Source: [Google spam policies](https://developers.google.com/search/docs/essentials/spam-policies).
